Design notes
------------
- NodeIds are dense and sequential so they can index side tables directly.
  Later passes must store their results in side tables keyed by NodeId rather
  than mutating the AST, which stays immutable after parsing.
- NodeId::DUMMY marks nodes synthesised during error recovery. It deliberately
  panics on .index() so a dummy can never silently corrupt a side table.
- Pattern exists as a minimal stub (wildcard + binding only) because MatchArm
  needs it; the full set lands in 2.6.
- ExprKind::Block's value is defined as its last expression statement.
- StmtKind::Let/ForIn bind a plain Ident, not a Pattern - destructuring, if it
  lands at all, is a 2.6+ concern once Pattern is fleshed out.
- StmtKind::While/ForIn bodies are typed as Block (not Expr) since loop bodies
  are always braced; only If reuses Expr for its arms.
- Type exists as a minimal stub (named types only, in ty.rs) because item
  signatures (fn params/return, struct fields, enum variant payloads) need
  something to point at; generic args, arrays, references and fn types land
  in 2.5.
- ItemKind::Fn/Struct/Enum carry `generics: Vec<Ident>` (bare type-parameter
  names only, no bounds - nex has no traits in v0.1).
- Use is just a `::`-separated path (no `as` aliasing or `{}` groups yet).
- Mod's `items: Option<Vec<Item>>` distinguishes `mod foo;` (None, external
  file) from `mod foo { ... }` (Some, inline).
- ItemKind::Impl is a deliberate stub: just the target type's Ident, no method
  bodies. Real impls need Fn items nested inside plus the type system wired
  through, so this is intentionally left thin until later.
- No visibility (`pub`) on any item yet - not asked for by this step; add it
  when a step actually needs module-level exports to matter.
