Design notes
------------
- NodeIds are dense and sequential so they can index side tables directly.
  Later passes must store their results in side tables keyed by NodeId rather
  than mutating the AST, which stays immutable after parsing.
- NodeId::DUMMY marks nodes synthesised during error recovery. It deliberately
  panics on .index() so a dummy can never silently corrupt a side table.
- Pattern (pattern.rs) now covers Wildcard, Binding, literals (Int/Float/
  Str/Bool flattened directly onto PatternKind, matching ExprKind's style),
  EnumVariant (path + payload fields, empty fields for a unit variant),
  Struct (name + FieldPattern list), and Tuple.
- ExprKind::Block's value is defined as its last expression statement.
- StmtKind::Let/ForIn bind a plain Ident, not a Pattern - destructuring, if it
  lands at all, is a 2.6+ concern once Pattern is fleshed out.
- StmtKind::While/ForIn bodies are typed as Block (not Expr) since loop bodies
  are always braced; only If reuses Expr for its arms.
- Type (ty.rs) now covers Named (with generic args), Array, Ref, and Fn.
  TypeKind::Named changed from a bare `Named(Ident)` tuple to a
  `Named { name, args }` struct variant when generics were added in 2.5; the
  2.4 item-AST snapshots were regenerated to match, no semantic change.
- No path-qualified named types yet (`std::io::Read`) - Named.name is a
  single Ident. Add path segments only when an actual step needs them.
- ItemKind::Fn/Struct/Enum carry `generics: Vec<Ident>` (bare type-parameter
  names only, no bounds - nex has no traits in v0.1).
- Use is just a `::`-separated path (no `as` aliasing or `{}` groups yet).
- Mod's `items: Option<Vec<Item>>` distinguishes `mod foo;` (None, external
  file) from `mod foo { ... }` (Some, inline).
- ItemKind::Impl is a deliberate stub: just the target type's Ident, no method
  bodies. Real impls need Fn items nested inside plus the type system wired
  through, so this is intentionally left thin until later.
- Item carries `is_pub` as of 4.8. Item::new is private by default and
  Item::new_pub is the other constructor, which kept every existing caller
  working. The pretty printer wraps a public item as `(pub (fn ...))`.
- Module (module.rs) is the ast root: one parsed file's Vec<Item> plus its
  own NodeInfo. Added in 3.1 because the parser needs an entry-point return
  type; phase 2 didn't need it since nothing parsed a whole file yet.
- Parser (parser.rs) wraps a `&[Token]` cursor: peek/advance/expect plus a
  recoverable Vec<ParseError>. advance() is a no-op at Eof so callers can't
  walk off the end. parse_module() handles `fn` items as of 4.5; anything
  else at the top level is reported and skipped so parsing terminates.
- parse_expr() (3.3) is a pratt loop. The precedence ladder lives in one
  table, infix_binding_power(), running lowest-to-highest: || && compare
  | ^ & shift +- */% then PREFIX_BP for unary. Left-associativity is
  encoded as right_bp = left_bp + 1; there are no right-assoc operators
  yet. Comparisons are left-associative rather than non-associative as in
  rust, so `a < b == c` parses instead of erroring - revisit if that turns
  out to confuse rather than merely be useless.
- parse_leaf() (3.2) handles Int/Float/Str/Bool/Ident. On a
  token that can't start an expression, it records a ParseError and returns
  ExprKind::Unit with NodeInfo::dummy(span) as the recovery placeholder -
  reusing Unit rather than adding a dedicated error-expression kind, since
  the dummy NodeId already makes synthesized nodes distinguishable from a
  real `()` the source wrote. Revisit if that conflation ever causes a
  problem once the type checker exists.
- parse_paren() (3.4) makes `(a)` produce `a` with a widened span rather
  than a wrapper node, so redundant parens leave no trace in the AST; `()`
  is the unit literal. parse_block() parses `{ a; b }` into expression
  statements only - let/return/loops arrive in phase 4. Both the block's
  statement loop and its trailing `}` bail out through expect() on Eof, so
  an unterminated block reports one message and cannot spin (advance() is
  a no-op at Eof, so a naive loop would never make progress).
- parse_postfix() (3.5) loops call/field/index after the leaf, so they
  bind tighter than the prefix operators: `-a.b()` negates the call's
  result. Argument lists allow a trailing comma and break on Eof as well
  as `)`, since neither parse_expr nor expect consumes anything at Eof.
- struct literals (3.6) create the classic `if x { }` ambiguity, so the
  parser carries a no_struct_literal flag: when set, `Ident {` reads as
  "expression, then a block" instead of a struct literal. Nothing sets it
  until `if` lands in 3.7. with_struct_literals() re-enables them inside
  any nested delimiter - parens, brackets, call args, block statements,
  and struct field values - where the ambiguity can't arise.
- if/else (3.7) activates the no_struct_literal flag for the condition
  only; the body is a normal block again. `else if` nests another
  if-expression in the else arm rather than adding a chain node.
- parse_block() returns early with a dummy NodeInfo when the opening `{`
  is missing, so one missing brace yields one diagnostic instead of also
  reporting the `}` that was never opened.
- match (3.8) parses every phase-2.6 pattern. `_` is spelled, not
  tokenised - it lexes as an ordinary identifier, so parse_ident_pattern
  checks the name. A leading `-` in a pattern is part of the literal, not
  a unary operator: patterns have nothing to negate at runtime.
  Single-segment names disambiguate by what follows: `(` -> enum variant
  payload, `{` -> struct pattern, otherwise a binding.
- CONFIRMED BLOCKER (predicted by the 2.8 coverage review): ExprKind has
  no path variant, so a `::`-qualified EXPRESSION won't parse. Patterns
  handle `Option::Some(v)` fine, but the spec's own sample scrutinee
  `match Option::Some(x) { .. }` is rejected with "expected `{`, found
  `::`". Covered by a test asserting the current limitation.
- ranges (3.9) bind looser than every operator in infix_binding_power, so
  they fold in AFTER the pratt loop rather than before it - folding first
  was a real bug, it made `a + 1..b` stop at `(+ a 1)` and drop the range.
  Parsing the end at RANGE_BP+1 keeps them from chaining: `a..b..c` yields
  `a..b` and leaves `..c` unconsumed.
- ExprKind::Range needs both endpoints, so rust's open-ended `a..`, `..b`
  and `..` have nowhere to go in the AST yet. Add Option<Box<Expr>> when a
  step actually needs them.
- error recovery (3.10): synchronize() skips to the next statement
  boundary after a failed statement - consuming a `;`, stopping before a
  `}` so the enclosing block can still close, and stopping at Eof so it
  always terminates. The block loop compares the error count before and
  after each statement to decide whether to synchronize, so a block
  reports every broken statement instead of only the first.
- ariadne (3.11) replaced the hand-rolled renderer in nex-driver/diag.rs.
  Pinned to =0.5.1: 0.6.0 does not build on our 1.83 msrv (it uses
  f32::max/min in a const fn). Colour is off so output is stable in tests
  and when piped. IMPORTANT: nex spans are BYTE offsets but ariadne's
  Source indexes by CHARACTER, so diag.rs converts - without it a
  multi-byte char earlier in the line shifts the reported column right.
  Empty spans (the Eof token has one) are widened by a char, since
  ariadne panics on an empty range.
- StmtKind::Let gained `ty: Option<Type>` in 4.1; the ast had no room for
  the annotation before. parse_type covers named types with generic args,
  [T], &T and fn(..) -> T.
- `Vec<Vec<T>>` does not parse: `>>` lexes as one shift token so the inner
  `>` closes nothing. Needs the lexer or parser to split it.
- StmtKind::Assign (4.2) holds an Expr target rather than a name, so
  `a.b[0] = 1` parses; whether the target is actually assignable is left
  to the type checker. `op: Option<BinaryOp>` is None for a plain `=`.
  parse_stmt parses an expression first and only then looks for an
  assignment operator, since the two start out identical. Assignment is a
  statement, not an expression, so `x = y = 1` does not chain.
- return (4.3) treats the value as optional by looking ahead for `;`, `}`
  or Eof, so `return` at the end of a block is bare rather than trying to
  parse the brace as an expression.
- loops (4.4) put the header in without_struct_literals, same as an if
  condition, so `while x { }` is a loop rather than a struct literal.
- a statement ending in a braced body needs no `;` before the next one
  (needs_semi in parser.rs), matching rust. Without this `while a { } b`
  was a parse error, since the block loop treated a missing semicolon as
  the end of the block. Found by parsing the spec's sample main(), which
  now parses clean end to end and is pinned by a test.
- fn items (4.5) parse generics, params, an optional `-> ret` and a body.
  examples/hello.nex now parses as a whole file, pinned by a test.
- struct items (4.6). Two error-recovery fixes came out of this: parse_type
  no longer consumes closing delimiters (`}` `)` `]` `>` `,` `;`) when it
  fails, since eating a `}` stripped the enclosing struct of its brace and
  cascaded; and a missing `:` in a field or param skips the type parse
  rather than reporting the same mistake twice.
- enum items (4.7) parse unit and tuple variants. The plan text for this
  step also lists STRUCT variants, but language-design.md has no syntax for
  them anywhere (its only enum is `enum Option<T> { Some(T), None }`) and
  Variant.fields is a Vec<Type> with no room for names. Built what the spec
  defines rather than inventing a feature; needs a decision before the spec
  freezes in phase 7.
- examples/tour.nex is now blocked by exactly two known gaps: the `const`
  item (plan step 7.11) and the path expression `Option::Some(x)`. Pinned
  by a test that fails once either is fixed.
- use/mod/pub (4.8). parse_item() returns Option<Item> and reports nothing
  itself, so both parse_module and an inline `mod { }` body can decide
  whether a non-item means "error" or "end of list". `mod foo { }` recurses
  through parse_item, so mods nest and `pub` works inside them.
- parser fuzzing (4.11) mutates hello.nex and tour.nex 10k times each and
  checks the parser never panics. A third test asserts non-empty input
  always produces items or errors, which catches the parser stalling -
  a plain no-panic check would not.
- Value (nex-interp, 5.1). Heap values (str, array, struct, enum, fn) sit
  behind Rc so cloning a Value is cheap and two bindings share the same
  array. Arrays and struct fields are RefCell for mutation later.
- Only Bool is truthy; as_bool() returns None for everything else, so the
  interpreter can reject `if 1 { }` rather than inventing a conversion.
- Display is what `print` writes: strings bare, floats keeping their `.0`
  so they stay distinguishable from ints. Debug quotes strings instead.
- Fn values compare by Rc identity. Comparing bodies would be surprising
  and comparing names would be wrong.
- Scope (5.2) is a linked chain rather than a stack of frames: each holds
  an Rc to its parent, so a closure capturing a scope keeps it alive after
  the call that made it returns. define() shadows, assign() walks outwards
  to the nearest existing binding and fails if there is none - creating
  bindings is `let`'s job, not assignment's.
- eval (5.3) covers literals, identifiers and operators. Integer
  arithmetic is CHECKED: overflow, division by zero and out-of-range
  shifts are runtime errors rather than wrapping or panicking. Floats
  follow ieee, so 1.0/0.0 is infinity - only integers error there.
- No implicit conversions anywhere: `1 + 1.0` and `1 == 1.0` are both
  errors, and only Bool is accepted as a condition.
- `&&` and `||` short-circuit, so `false && undefined` is false rather
  than an undefined-name error.
- Step 5.4 (floats, string concat, comparisons) is already covered by
  5.3's implementation and tests; it needs confirming rather than
  writing.
- pretty.rs (print_expr/print_stmt/print_item/print_type/print_pattern)
  renders the whole AST as s-expressions for snapshot tests. It is one-way
  (not meant to be reparsed) and lossy on purpose: no spans, no NodeIds,
  just shape - that's what makes the snapshots readable.

Lint enforcement
----------------
- clippy::cognitive_complexity is now wired in: `[workspace.lints.clippy]`
  in the root Cargo.toml sets it to "warn", each crate opts in via
  `[lints] workspace = true`, and the threshold lives in clippy.toml
  (cognitive-complexity-threshold = 20). It composes with CI's existing
  `cargo clippy -- -D warnings` rather than needing a separate command.
  Verified both ways: the real threshold (20) passes clean with real
  headroom (worst offenders today sit at 16 and 19), and dropping it to 1
  makes the exact same CI command fail (29 violations, exit 101) -
  confirming the lint is actually wired in, not just quietly allowed.
